I maintain [Hacé Cuentas](https://hacecuentas.com), ~2,700 calculators where each one is a JSON content file plus a TypeScript formula module. The scary part of a site like this isn't the page that 500s — that's loud. It's the calculator that **looks fine, computes, and quietly returns `NaN`, `Infinity`, or the wrong number.** Nobody files a bug. The page just slowly bleeds trust.

The dev server doesn't help here: it renders the page, but it doesn't actually *run* every formula with real inputs. So I built a headless harness that does.

## The core idea

Every formula is registered by id:

```ts
// src/lib/formulas/index.ts  (autogenerated)
export const formulas = {
  'plazo-fijo': plazoFijo,
  'imc': imc,
  'aguinaldo-sac': aguinaldoSac,
  // ...one entry per calc
};
```

And every content JSON declares default/representative field values. So I can, outside the browser, load the content, build an input object, call the formula, and assert the output is sane:

```ts
import { formulas } from '../src/lib/formulas';
import { loadAllCalcs } from './lib/load-calcs';

let broken = 0;

for (const calc of loadAllCalcs()) {
  const fn = formulas[calc.formulaId];
  if (!fn) { console.error(`✗ ${calc.slug}: no formula for id ${calc.formulaId}`); broken++; continue; }

  const inputs = Object.fromEntries(
    calc.fields.map((f) => [f.id, f.default ?? sampleFor(f)])
  );

  let out;
  try { out = fn(inputs); }
  catch (e) { console.error(`✗ ${calc.slug}: threw ${e.message}`); broken++; continue; }

  for (const o of calc.outputs) {
    const v = out[o.id];
    if (v === undefined || (typeof v === 'number' && !Number.isFinite(v))) {
      console.error(`✗ ${calc.slug}: output "${o.id}" = ${v}`);
      broken++;
    }
  }
}

console.log(broken ? `${broken} broken` : 'all formulas OK');
process.exit(broken ? 1 : 0);
```

Run it with `tsx`, no browser, no dev server. It walks the *registry*, not the pages, so a calc that exists but was never wired up (JSON present, `formulaId` pointing at nothing) gets caught immediately.

## The classes of bug it actually found

Running this across the whole catalog surfaced things I'd never have found by clicking:

- **Orphan `formulaId`.** A handful of calcs referenced a formula id that had no module — the page rendered, the button did nothing. Silent.
- **Division by zero → `Infinity`.** A financing calc divided by a term that could be `0` from a default. Output card showed `$Infinity`.
- **Boolean-from-`<select>` footgun.** `!!inputs.someFlag` where the select returned the *string* `"false"` — which is truthy. The calc took the wrong branch for everyone who didn't touch that field.
- **Locale formulas that never matched.** Some country-specific variants had a `formulaId` that didn't exist in the registry at all, so they fell through to nothing.

None of these throw. None of these 500. They just give a confidently wrong answer, which on a calculator is the worst failure mode there is.

## Reverse-checking the result

Catching `NaN` is table stakes. The subtler harness runs a **reverse check**: for formulas that are invertible, feed the output back and confirm you recover the input within tolerance. That catches the off-by-a-factor bugs (a rate applied as `0.21` vs `21`) that produce a finite, plausible-looking, completely wrong number.

```ts
const out = fn(inputs);
const back = inverse(out);              // formula-specific
assertClose(back.principal, inputs.principal, 0.01);
```

A "finite and plausible" wrong answer is exactly what no smoke test catches and what users can't tell is wrong. This is the check that earns its keep.

## Why not just unit-test each formula?

I do have unit tests for the gnarly ones. But 2,700 hand-written test files is its own maintenance bomb. The harness gives me **coverage of the whole catalog for free** — every new calc is automatically included the moment its JSON lands, because the harness enumerates the registry. Unit tests go where the math is genuinely tricky; the harness is the floor that guarantees nothing is silently dead.

## Takeaways

- For data/content-driven sites, render tests aren't enough — **run the logic headless against your registry.**
- Assert `Number.isFinite`, not just "no exception." The dangerous bugs are finite.
- Enumerate the registry, not the pages, so unwired content can't hide.
- Add a reverse check for invertible formulas to catch off-by-a-factor errors that look plausible.
